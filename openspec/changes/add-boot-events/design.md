# Design: add-boot-events

## Context

Конвейер: `traps/doors/health → raw → allowlist+enrich → aggregator → notices → Telegram`, плюс `direct`-канал для плановых текстов сторожа (runtime.go). Двери задают платформенный паттерн: `runDoors` → `doors_windows.go`/`doors_linux.go` → `internal/doors` (winlog через wevtapi `EvtSubscribe`, journald через `journalctl -o json`). Чтение Security-канала требует Event Log Readers; System-канал — нет. Состояние сторожа живёт в `cfg.DataDir` (`health` пишет свой state) — туда же ляжет состояние загрузки.

Детект возможен только post-factum: в момент выключения агент уже остановлен. Старт службы после автозагрузки — точка, где система уже готова ответить «что было до меня».

## Goals / Non-Goals

**Goals:**
- Один алерт на каждую реальную загрузку машины, немедленно, на Windows и Linux.
- Классификация прошлой сессии: штатно/аварийно, инициатор (когда источник отдаёт), действие (перезагрузка vs выключение→включение), простой.
- Ноль ложных срабатываний на рестарт службы (обновление, stop/start из пульта, крэш).

**Non-Goals:**
- Алерт в момент выключения (агент к этому моменту мёртв; ингибиторы/systemd-shutdown — хрупко).
- Сон/пробуждение, гибернация как события (boot identity не меняется — не алертим).
- Ключ конфига для отключения датчика.
- Настройка текста алерта владельцем.

## Decisions

- **D1: Детект по идентификатору загрузки + файл состояния `data/boot.json`.** Linux — `/proc/sys/kernel/random/boot_id` (стабильный UUID на загрузку); Windows — `LastBootUpTime` (WMI Win32_OperatingSystem через `wmi`-пакет уже в зависимостях? проверить; иначе PowerShell-подзапрос как у прочих внешних вызовов). Совпадение — рестарт службы, молча. Первый запуск (нет файла) — запись без алерта. Альтернатива «аптайм < N минут» отвергнута: пороги хрупки, WMI boot time надёжен.
- **D2: Новый one-shot-компонент `boot` в `runAgent`.** `run("boot", ...)`: проверил → эмитнул → вернул nil (компонент не держит цикл). Эмит — в `direct` (немедленная доставка), минуя raw/aggregator: событие одиночное и самоценное, окно агрегации только задержало бы его. Название Kind: `machine_boot`.
- **D3: Windows — исторический запрос `EvtQuery` по System-каналу.** К `winlog_windows.go` добавляется `EvtQuery`+`EvtNext` (те же wevtapi-практики, что у `EvtSubscribe`), XPath за окном прошлой сессии: 1074 (USER32: TargetUser/Domain, процесс, Reason, действие), 6006 (штатное завершение EventLog), 6008 (аварийное), 41 (Kernel-Power, грязное). Классификация: есть 6006 или 1074 с действием завершения — штатно; иначе аварийно. Инициатор — из самой свежей 1074. Элевейшн не нужен (System-канал читается обычным пользователем), зависимости от Event Log Readers нет.
- **D4: Linux — хвост прошлого бута через `journalctl -b -1 -n 200`.** Штатность: присутствие `Reached target Reboot` / `Reached target Power-Off` в хвосте; отсутствие — аварийно. Инициатор: строка `sudo[..]: user : ... COMMAND=...reboot|shutdown|poweroff` (sudo логирует в journald) — best-effort, отсутствие не портит алерт. Действие (reboot vs poweroff) — по маркеру target. Простой: последняя метка времени бута −1 vs метка старта текущего. Всё парсится чистыми функциями над выводом journalctl — тестируемо на фикстурах, как `ParseSSHMessage`.
- **D5: Порядок компонентов не важен, состояние — только у boot.** Boot не зависит от traps/doors (пишет в direct напрямую). Сбой классификации (журнал недоступен) — деградация до алерта уровня 1 («загрузилась, детали недоступны») с warn в лог, не отказ.
- **D6: Формат алерта** — единый текст с блоками: факт (загрузилась/перезагрузилась), классификация (штатно/аварийно), инициатор, простой. Стилистика существующих алертов (машинный ярлык + детали), маска в notify по образцу дверей.

## Risks / Trade-offs

- [Windows Fast Startup: «Завершение работы» — гибернация ядра, журнал может выглядеть как resume] → классификация может соврать на десктопе с fast boot; фиксируем как известное ограничение, проверяем живой прогон (Kernel-Boot event 27 различает boot type, можно уточнить при приёмке).
- [У Windows-агента служба может быть остановлена владельцем надолго] → алерт уйдёт при следующем старте службы с фактическим временем загрузки; не теряется, а откладывается.
- [Потеря `data/boot.json`] → один пропущенный алерт (первый запуск), состояние самовосстанавливается.
- [Инициатор на Linux недоступен без sudo-логирования] → best-effort по контракту спеки.
- [WMI-запрос LastBootUpTime на каждой старте] → один запрос за старт агента, стоимость незначима.

## Migration Plan

Аддитивно: новый Kind, новый компонент, новое состояние. Старые конфиги и спеки не меняются. Откат — исключить компонент `boot` из конвейера; `data/boot.json` безвреден.
