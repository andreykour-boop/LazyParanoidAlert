# Design

## Context

Агент — один бинарник `cmd/siren` с тремя уже разделёнными режимами: SCM-хост (`svc.IsWindowsService()`), CLI управления службой (`-service …`) и консольный запуск конвейера. Конфиг читается `config.Load` (валидация, BOM-tolerance), служба ставится как LocalSystem с автостартом. Зависимости проекта: только `x/crypto`, `x/sys`, без cgo, кросс-сборка linux из Windows. Мотивация — см. proposal.md (Why).

## Goals / Non-Goals

Goals:
- Окно управления + трей в том же `siren.exe`, без второго файла и без инсталятора.
- Редактирование конфига через форму с валидацией и применением перезапуском службы.
- Нулевое изменение поведения ловушек/датчиков/доставки.

Non-Goals:
- Живой мониторинг событий в окне (остаётся в Telegram).
- Удалённый доступ к UI, мультитенантность, Linux-аналог формы.
- Новые эмуляторы и новые поля конфига (кроме, возможно, сериализации существующих).

## Decisions

### 1. Библиотека UI: lxn/walk (нативные Win32-виджеты)

Варианты: walk / go-webview2 / веб-UI на stdlib / PowerShell WinForms.

- **walk** — выбран: настоящая форма с чекбоксами и кнопками (то, что просил пользователь), pure Go без cgo, включает NotifyIcon (трей) в той же библиотеке. Минус: проект не развивается — принято, потому что потребность ограничена примитивными виджетами, а UI изолирован в `ui_windows.go` (build tag windows): при необходимости UI заменяется на веб-страницу без изменений бэкенда.
- go-webview2 отклонён: HTML/JS-ассеты и JS-мост усложняют код ради той же функциональности.
- Веб-UI на stdlib отклонён: «открылся браузер» ломает сценарий «жмакнул и забыл».
- PowerShell WinForms отклонён: дублирование схемы конфига в двух языках — ровно тот долг, которого проект избегает.

### 2. Подсистема exe — windowsgui, консоль прячется программно

Двойной клик не должен открывать чёрное окно. Бинарник собирается с `-H=windowsgui`; при запуске из терминала (определяется по `GetConsoleWindow` + `GetConsoleProcessList`: консоль принадлежит текущему процессу и есть другие вкладчики) вызывается `AllocConsole`-подобный путь либо консоль просто остаётся. Для SCM и службы подсистема не важна.

Альтернатива (два бинарника: консольный и GUI) отклонена — противоречит «один файл, скопировал и забыл».

### 3. Всегда от администратора (manifest requireAdministrator)

Окно и трей запускаются elevated: кнопки службы работают без перезапуска себя через ShellExecute `runas`, запись конфига в `%ProgramFiles%\siren` возможна. UAC при каждом двойном клике принят пользователем сознательно. Manifest встраивается при сборке через rsrc-объект (`.syso`), исходник манифеста — в репозитории.

### 4. Одиночный экземпляр: named mutex + named event

При старте интерактивного режима создаётся mutex `Local\siren-ui`; если он уже существует — процесс выставляет named event `Local\siren-ui-open` (первый экземпляр ждёт его горутиной и открывает окно поверх) и завершается. Альтернативы (окно-хаб через FindWindow/WM, TCP-порт на localhost) отклонены: событие проще и не занимает порты, которые может захотеть слушать ловушка.

### 5. Потоки: конвейер — горутина, UI — главный поток

walk требует main-поток с STA. В интерактивном режиме `main()` запускает `runAgent` в горутине (как в svc-хосте), а UI-цикл walk живёт на главном потоке; завершение агента — по закрытию окна/выходу из трея, остановка конвейера — через существующий ctx-механизм.

**Важно (уточнено при реализации): конвейер в интерактивном режиме стартует только когда SCM-служба НЕ работает.** Если служба установлена и Running, интерактивный экземпляр — только пульт управления (настройки + кнопки), без своего конвейера: второй конвейер дрался бы со службой за те же порты ловушек и дублировал бы алерты в Telegram. Если служба не установлена/остановлена — интерактивный запуск сам работает как агент. Изменения конфига из формы применяются к обоим владельцам: к своему конвейеру (restart по ctx) и/или к службе (stop+start через `serviceCommand`).

### 6. config.Save с валидацией до записи

Зеркально к `Load`: сериализация текущей структуры, прогон той же валидации (порты, эмуляторы, telegram), запись через временный файл + rename (не оставить поломанный конфиг). Форма всегда стартует с `config.Load` актуального файла. Изменения применяются только перезапуском службы — служба читает конфиг один раз на старте, поэтому IPC не нужен.

### 7. Кнопки службы переиспользуют существующий код

`serviceCommand` уже реализует install/start/stop/remove/status — форма вызывает те же функции в процессе (не через exec самого себя), статус опрашивается `mgr` раз в несколько секунд при открытом окне.

## Risks / Trade-offs

- [walk не развивается, потенциальные дыры совместимости с будущими Windows] → UI изолирован в файлах с build tag windows; деградация чинится заменой только UI-слоя.
- [UAC на каждый запуск раздражает] → принято пользователем; альтернатива с on-demand elevation усложняет single-instance и оставляет окно без прав на запись конфига.
- [Антивирус может не любить windowsgui + requireAdministrator + трей] → легитимный подписанный сценарий отсутствует; при срабатывании — исключение каталога агента (уже практикуется на этой машине).
- [Конфиг в Program Files правится elevated-UI] → окно всегда elevated, конфликтов прав нет; файл пишется атомарно (tmp+rename).
- [Терминальный запуск с windowsgui не показывает stdout] → для отладки лог и так пишется в файл; при необходимости `-console` форсирует AllocConsole. (Точный механизм фиксируется при реализации, на спеку не влияет.)

## Migration Plan

1. Сборка: build.ps1 добавляет шаг генерации .syso (manifest/icon); остальные шаги без изменений.
2. Windows-комплект: exe заменяется на новый; install.ps1 остаётся как тихий путь для Hermes, ручной путь — «скопировать, запустить, тыкнуть».
3. Уже установленная служба на целевых машинах совместима: exe тот же путь и флаги; обновление = остановить, заменить файл, запустить (или кнопкой в новой форме).
4. Откат: вернуть прежний exe — конфиг и служба совместимы в обе стороны (схема конфига не меняется).
