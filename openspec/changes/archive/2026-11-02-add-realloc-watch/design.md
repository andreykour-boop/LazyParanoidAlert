# Design

## Context

Рендеры (панель `renderPanelBody`, отчёт `SnapshotText`) уже печатают «— realloc N, pending N», когда поля `L1Disk` заполнены — на Linux их заполняет smartctl. На Windows L1 собирается из WMI `MSFT_PhysicalDisk` (HealthStatus без SMART-атрибутов), поэтому цифры не приходят. Проверено на живой машине: классы `MSStorageDriver_FailurePredictData/Status` в `root\wmi` присутствуют; чтение требует элевации — служба работает как LocalSystem, пульт собран с requireAdministrator-манифестом, т.е. оба рантайма имеют доступ. smartctl на Windows-машине не установлен. Диф сторожа (`Diff`) тревожит только на смену статуса/состава и violation места — рост realloc при статусе «ok» проходит молча (кейс сервера: sda realloc 481).

## Goals / Non-Goals

**Goals:**
- realloc/pending в L1 на Windows без внешних зависимостей.
- Немедленная тревога на рост realloc на обеих платформах.
- Ноль новых строк-заполнителей и фиктивных ошибок в рендерах.

**Non-Goals:**
- Установка smartmontools на Windows (путь через `findTool("smartctl")` остаётся опцией на будущее).
- Температура и прочие SMART-атрибуты (парсер делаем общим, но собираем только 5 и 197).
- Тревога на рост pending (шумнее: pending флапает при ремапах; в статус попадает через Reason).
- Алармы в UI пульта (панель только читает снимки).

## Decisions

**D1. Источник на Windows — WMI `root\wmi\MSStorageDriver_FailurePredictData`, а не smartctl/StorageReliabilityCounter.**
`Get-StorageReliabilityCounter` не содержит поля realloc (только Wear/ReadErrors*/Temperature) — отпадает. smartctl даёт максимум данных, но требует установки smartmontools; отказ от внешних зависимостей важнее (см. proposal). WMI-SMART уже присутствует на машине и доступен обоим нашим рантаймам. Транспорт данных — powershell (`Get-CimInstance` + base64 VendorSpecific + JSON): прямая go-ole-путь через IDispatch доставляет SAFEARRAY повреждённым (512 байт 0xFF, подтверждено smartprobe на живой машине), powershell читает те же данные корректно. Ограничение класса — только ATA/SATA — принимаем: USB/NVMe диски показываются без счётчиков, честно и без ошибок.

**D2. Парсер SMART-таблицы — чистая кроссплатформенная функция.**
`VendorSpecific` — это стандартный 512-байтный SMART READ DATA буфер: WORD версии, далее до 30 записей по 12 байт: id (1), флаги (2), текущее значение (1), raw (8, счётчики в little-endian первых байтов raw). Функция `parseSMARTAttributes(raw []byte) map[byte]uint64` (id → raw-значение) без сборочных тегов, тестируется на фиксируемом blob; сборщики атрибутов 5 и 197 — в платформенном файле. Невалидная/короткая таблица → пустая карта (не ошибка).

**D3. Сопоставление атрибутов с дисками — через PNPDeviceID.**
`MSStorageDriver_FailurePredictData.InstanceName` соответствует `PNPDeviceID` из `Win32_DiskDrive`, у которого есть и SerialNumber, но в одном из двух написаний: на живой машине PNPDeviceID имеет вид `SCSI\DISK&VEN_TOSHIBA&PROD_MD04ACA600\5&3955AA6&0&030000`, а InstanceName — `SCSI\DiskTOSHIBA_MD04ACA600\5&3955aa6&0&030000` (для старых IDE — `IDE\Disk...` с обеих сторон). Ключи сопоставления: префикс из первых двух сегментов (покрывает IDE-написание) и хвостовой devnode-сегмент `5&3955aa6&0&030000` (идентичен в обоих написаниях, покрывает SCSI) — серийник → PNPDeviceID → префикс, при промахе хвост. Резерв при недоступности Win32_DiskDrive — нормализованное сравнение моделей из InstanceName. Не найденному диску счётчики не присваиваются (не ошибка). Два одинаковых диска: сопоставление по серийнику устраняет двусмысленность; без серийника — первая свободная пара (принимаемый риск, редкий случай).

**D4. Тревога роста — новый вид изменения в `Diff`.**
Kind `realloc_growth` (по образцу существующих `source_lost`/`status_changed`): сравнение по диску (Name + Serial), только на увеличение (уменьшение счётчика физически невозможно и игнорируется), любое изменение ≥ 1. Detail: «realloc 481 → 482». Естественная дедупликация расписанием: тревога только при фактическом изменении между проверками — при стабилизации счётчика повторы не спамят. Runner кладёт это в обычный конвейер `Alarm`, формат сообщения — как у существующих дисковых тревог.

**D5. Рендеры не меняются.**
Панель и `SnapshotText` уже выводят счётчики при заполненных полях; агрегация счётчиков в снимок не меняет форматов. README дистрибутивов дополняется одной строкой про счётчики и тревогу роста.

## Risks / Trade-offs

- **Покрытие WMI-SMART не полное** (USB-мосты, NVMe, часть RAID-контроллеров не прокидывают атрибуты): компенсируется честным отсутствием цифр; для контроллеров за vendor-CLI счётчики уже приходят через smartctl-путь vendor-cli.
- **Хрупкость сопоставления по модели** при недоступности `Win32_DiskDrive` и двух одинаковых дисках: счётчики могут попасть не тому диску; риск ограничен случаем идентичных моделей без серийников.
- **Шум тревог при активной деградации**: диск с растущим realloc будет тревожить на каждой проверке, пока счётчик растёт — это желаемое поведение (растущий realloc = активная деградация).
- **WMI-семантика «normalized вместо raw» (обнаружено посмертной сверкой со smartctl 7.5)**: на живой машине WMI-драйвер кладёт в raw-позиции VendorSpecific нормализованное значение (у TOSHIBA realloc/pending = 100 при фактическом raw 0/0 по smartctl; smartctl-сверка — тот же диск, serial совпадает). Панельные цифры остаются показателем здоровья, но рост секторов в этой семантике выглядит как падение value — `realloc_growth` на таких машинах не сработает. Принято: смену источника не делать в этом change; smartmontools 7.5 установлен, smartctl проверен (правильные raw + NVMe + USB-частично), подключение smartctl как основного источника на Windows (WMI — фолбэк) оформляется следующим change (`add-nvme-health`).
- **Деплой-нюанс smartmontools**: NSIS-установщик добавляет `smartmontools\bin` только в пользовательский PATH — служба (LocalSystem) его не увидит; будущему smartctl-источнику нужен явный поиск в `C:\Program Files\smartmontools\bin`.
