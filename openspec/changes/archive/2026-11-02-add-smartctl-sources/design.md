# Design

## Context

Сторож уже мультиисточниковый: на Linux smartctl собирает L1 (`smartctlSource` из `/sys/block` + `parseSmartctl`), mdadm — L2; на Windows L1 собирается из `MSFT_PhysicalDisk` (COM/PowerShell), счётчики SATA обогащаются через `root\wmi`, диски за RAID — через vendor-cli с текстовым парсером smartctl. Контракт источников: отсутствие инструмента — не ошибка конструкции, источник регистрируется и честно отчитывается при сборе.

События, определившие дизайн (живая машина, Windows):
- WMI-путь отдаёт raw-позиции VendorSpecific с **normalized** значением (TOSHIBA: realloc/pending = 100 при фактическом raw 0/0 по smartctl; serial совпадает — сверка того же диска). Рост секторов в этой семантике выглядит как падение value — `realloc_growth` не сработает.
- smartmontools 7.5 установлен на обеих машинах; версии совпадают → формат `-j` (JSON) одинаков.
- Текстовый вывод smartctl печатает NVMe-счётчики с разделителями тысяч (locale) — текстовый `ParseInt` молча ломается на многозначных числах.
- NSIS-установщик smartmontools прописывает `smartmontools\bin` только в пользовательский PATH; служба работает как LocalSystem и его не увидит.
- `smartctl --scan` на Windows не показывает USB-диск (Seagate Expansion) — мост не прокидывает SMART.

См. proposal.md (Why) для мотивации; требования — в delta-спеке.

## Goals / Non-Goals

**Goals:**
- Одинаковый, честный набор счётчиков (SATA: realloc/pending raw; NVMe: media errors/wear) на обеих платформах через smartctl.
- Зондирование источников на живой машине при сборе, без «заточки» под конкретное железо: инструменты coexistят, приоритет по качеству, отсутствие — честное.
- Защита diff от смены источника (провенанс счётчиков).
- Ноль новых строк-заполнителей и фиктивных ошибок в рендерах.

**Non-Goals:**
- Замена vendor-cli пути (RAID-контроллеры) — он остаётся на текстовом парсере.
- Алармы на wear (Percentage Used монотонно растёт всю жизнь диска — аларм на каждый +1% был бы шумом), на Available Spare и Unsafe Shutdowns (покрывается статусом: деградация spare отражается в Critical Warning → smartctl ставит FAILED → срабатывает существующий `status_changed`).
- Поддержка USB-мостов (`-d sat`-эксперименты с конкретными мостами) — USB остаётся без счётчиков, честное отсутствие.
- Удаление WMI-кода — он становится фолбэком.
- Тревога на рост pending (без изменений из предыдущего change).

## Decisions

**D1. smartctl — основной источник счётчиков на Windows; WMI — фолбэк.**
Альтернативы: оставить WMI основным для SATA (отвергнуто: доказанная normalized-семантика делает realloc_growth неработоспособным), использовать smartctl только для NVMe (отвергнуто: два SMART-пути для одного класса дисков, SATA-семантика остаётся сломанной). Порядок на Windows: smartctl найден → счётчики оттуда для всех дисков, что он видит; не найден → WMI-обогащение, как сейчас. Логика выбора живёт в точке сборки L1, оба пути остаются injectable для тестов.

**D2. Прямой smartctl-путь — на JSON (`-j`).**
`smartctl -i -H -A -j <device>` на обеих платформах (7.5 в обоих местах). JSON даёт чистые числа без locale-разделителей (текстовый вывод NVMe-счётчиков содержит разделители тысяч — доказано живым выводом «14 974») и стабильную структуру между версиями. Новые поля берутся из `ata_smart_attributes.table` (id 5, 197) и `nvme_smart_health_information_log` (`media_errors`, `percent_used`), идентичность — из `model_name`/`serial_number`, статус — из `smart_status.passed`. Текстовый парсер (`parseSmartctl`) сохраняется для vendor-cli пути без изменений.

**D3. Перечень устройств на Windows — `smartctl --scan`, сопоставление — по серийнику с модельным фолбэком.**
`--scan` возвращает devnode'ы (`/dev/sda`, `/dev/nvme0`); с каждым выполняется `-i -H -A -j`. L1-базой остаётся `physicalDiskSource` (Name/Model/Serial/Status из MSFT_PhysicalDisk); smartctl-запись сопоставляется с ней по нормализованному серийнику (`normSerial`). Живая проверка выявила: для NVMe MSFT_PhysicalDisk отдаёт вместо серийника EUI64-производный идентификатор (`0000_0000_..._0905.`), который никогда не совпадёт с `serial_number` из smartctl, — поэтому при промахе по серийнику работает фолбэк по нормализованной модели (`normID`, точное совпадение; модели «SSD AMD R3MP30512G8 512GB» совпадают с обеих сторон). Одинаковые модели: первая свободная запись, то же правило, что в WMI-фолбэке; вторая остаётся без счётчиков. Диск, которого нет в `--scan` (USB), остаётся без счётчиков. Альтернатива — строить L1 целиком из smartctl (отвергнуто: теряем FriendlyName и HealthStatus StorAge-провайдера, ломаем рендеры).

**D4. Провенанс счётчиков: источник хранится в записи диска, смена источника = перебазирование.**
`L1Disk` получает поле источника счётчиков (например, `CountersSrc string`, `omitempty`). В `Diff`: если источник счётчиков диска изменился между снимками — счётчики не сравниваются, новая база фиксируется молча (не тревога, не «не смог проверить»). Мотивация — доказанная семантическая несовместимость: переход smartctl → WMI выглядит как рост 0 → 100 (ложная тревога), WMI → smartctl как падение 100 → 0 (тишина и так, но база всё равно неверна). Поле попадает в state-файл без миграции (`omitempty`), старые state-файлы без него считаются «источник неизвестен» → перебазирование при первом новом снимке.

**D5. Тревога `media_error_growth` — отдельный kind, по образцу `realloc_growth`.**
Рост media_errors ≥ 1 по диску (Name + Serial), только увеличение, только при совпадении источника счётчиков (см. D4). Detail: «диск X: media errors 0 → 3». Отдельный kind (а не обобщение realloc_growth) — чтобы текст тревоги честно называл счётчик.

**D6. `findTool("smartctl")` дополняется кандидатами путей на Windows.**
`exec.LookPath` остаётся первым шагом; при промахе — перебор фиксированных кандидатов (`C:\Program Files\smartmontools\bin\smartctl.exe`), существование проверяется `os.Stat`. Кандидаты — только стандартные пути установки; конфигурируемость не добавляем (YAGNI, путь один). На Linux поведение не меняется.

**D7. Рендер: одна строка в `report.go`, панель — уже обобщённая.**
Отчёт печатает «— media errors N, wear N%» при заполненных полях (рядом с существующей строкой realloc/pending). Панель пульта переиспользует тот же текст снятка. Пустые поля не печатаются — никаких заполнителей.

## Risks / Trade-offs

- **smartctl требует элевации на Windows** (без прав — «Open failed, Error=5» на части devnode'ов) → служба (LocalSystem) и пульт (requireAdministrator) имеют доступ; не-elevated контексты (вручную запущенный `-health-report` из обычной консоли) увидят отсутствие данных так же, как сейчас с WMI. Проверяется живой проверкой.
- **`--scan` не показывает диски без SMART вообще** (USB) → приём: счётчиков нет, статус берётся из L1-базы (MSFT_PhysicalDisk), секция «не смог проверить» не пополняется.
- **Расхождение перечня `--scan` и `MSFT_PhysicalDisk`** (RAID-тома, дубли devnode) → сопоставление строго по серийнику; несопоставленные smartctl-записи молча отбрасываются (счётчики без диска-владельца не показываются).
- **JSON-парсер — новый код рядом со старым текстовым** → оба парсера покрыты фиксируемыми фикстурами (реальный вывод `smartctl -j` с живой машины — как фикстура); vendor-cli путь не трогается.
- **Перебазирование скрывает рост, случившийся точно в момент смены источника** → принимаемый риск: смена источника — редкое событие (установка/удаление smartmontools), следующая проверка уже сравнивает корректно.
- **wear (% used) у NVMe может отсутствовать** в JSON у части контроллеров → поле опционально, `omitempty`, отсутствие не ошибка.
