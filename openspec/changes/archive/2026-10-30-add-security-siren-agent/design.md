# Design

## Context

Доверенная LAN с доменом AD: Windows-машины с включённым RDP, Linux с работающим SSH, SMB и принтеры используются легитимно. См. proposal.md — Why. Существующего кода нет; проект начинается с этого change'а.

## Goals / Non-Goals

**Goals:**

- Один бинарник (Go) для windows/amd64 и linux/amd64, работающий как служба Windows / systemd-юнит.
- Ловушки на свободных портах с эмуляцией протоколов (баннер + минимальный диалог), подключившийся не должен распознать ловушку.
- Факты попыток и успешных входов на занятых портах: RDP (Windows Security/RemoteConnection events), SSH (journald).
- Обогащение событий: IP -> hostname (reverse DNS), MAC (ARP), ручная карта IP -> имя.
- Агрегация повторов (брутфорс, сканирование) и доставка в Telegram с учётом лимитов API.
- Индивидуальные тумблеры по портам и выбор эмулятора в конфиге.

**Non-Goals:**

- Инспекция полезной нагрузки трафика (включая HTTP-запросы) и дешифрование.
- Чтение журналов файрвола / аудита WFP / drop-логов.
- Ловушки на портах, занятых реальными сервисами (22 с sshd, 3389 с RDP).
- Полная маскировка от ручного глубокого фингерпринтинга (nmap -sV -A и т.п.) — целевой уровень: баннеры и диалоги аутентификации.
- Слежение за исходящими соединениями машины.

## Decisions

### Язык: Go

Один статический бинарник, тривиальная кросс-компиляция, горутины как естественная модель для множества слушателей и конвейера событий. Альтернатива (Python/PowerShell на каждой ОС отдельно) — две кодовые базы и рантайм на целевых машинах.

### Зависимости (минимум, всё официальное)

| Задача | Решение |
|---|---|
| Служба Windows | `golang.org/x/sys/windows/svc` |
| Подписка на события Windows | wevtapi `EvtSubscribe` (push-колбэк) через `x/sys/windows` + тонкий syscall-слой; API-поверхность минимальна (3 event ID в 2 журналах) |
| SSH-ловушка | `golang.org/x/crypto/ssh`: настоящий handshake, аутентификация всегда отклоняется — сканер видит честный SSH |
| journald | subprocess `journalctl -f -o json -u ssh`; нативный API требует cgo и ломает кросс-компиляцию |
| Telegram | чистый `net/http`, один метод API; без библиотек-обёрток |
| ARP | Windows: iphlpapi через `x/sys/windows`; Linux: `/proc/net/arp`/netlink |
| Reverse DNS | `net.LookupAddr` |
| TLS :443 | `crypto/tls`, self-signed сертификат генерируется при первом старте и сохраняется |
| Конфиг | JSON из stdlib, валидация при старте |

Итого две внешние зависимости (`x/sys`, `x/crypto`), cgo не используется нигде.

### Архитектура процесса

```
main
 +-- config loader (валидация при старте)
 +-- ловушки: goroutine-слушатель на порт, эмулятор как стратегия
 +-- датчик дверей: Win: EvtSubscribe -> канал; Lin: journalctl -> JSON -> канал
 +-- обогатитель: IP -> hostname (кэш с TTL) -> MAC (ARP-кэш)
 +-- агрегатор: окна по IP, дедуп, дайджесты
 +-- telegram client: очередь, retry, rate limit
 +-- slog собственного лога агента
```

Эмулятор — интерфейс-стратегия: `ssh`, `http`, `ftp`, `telnet`, `vnc`, `mysql-greeting`, `postgres-greeting`, `rdp-greeting`, `silent`. Текстовые протоколы — самодельные диалоги; SSH — `x/crypto/ssh`; RDP/СУБД — корректный первый пакет-приветствие и вежливый сбой далее.

### Источники фактов входов

- Windows: Security 4625 (неудачный вход, Logon Type 10), 4624 (успех, Type 10), Microsoft-Windows-TerminalServices-RemoteConnectionManager 1149 (IP источника RDP). Подписка через `EvtSubscribe`, фильтрация по ID до разбора.
- Linux: journald юнита `ssh`: `Failed password` (включая `invalid user`) и `Accepted password|publickey`; IP и учётка извлекаются парсером по реальным образцам сообщений с целевых машин.

### Агрегация и Telegram

Окно по IP: повторные события одного типа от одного IP копятся в счётчик; в Telegram уходит первое событие и периодический дайджест («N попыток с IP X за T минут»). Учитываются лимиты Bot API (~20 сообщ/мин в чат) и 429-ответы (backoff). Формат сообщения: машина, время, порт/протокол, IP + hostname + MAC, учётка (для входов), тип: попытка/вход/подключение к ловушке.

### Развёртывание и права

- Windows: служба; учётка с правом чтения Security-журнала (группа Event Log Readers). Привилегированные порты в Windows не требуют прав.
- Linux: systemd-юнит; группа `systemd-journal`; `AmbientCapabilities=CAP_NET_BIND_SERVICE` для портов <1024.
- Токен Telegram-бота — в конфиге с правами 0600 (Windows: ACL, ограничивающий доступ); не выносится в env по решению владельца.

### Дефолтный набор портов (профили ролей)

- `desktop`: датчики 80, 443, 3306, 5432, 1433, 6379, 27017, 23, 5900, 21, 69, 2049, 5985/5986; ловушки на всех свободных.
- `server`: без 80/443 по умолчанию (легитимный трафик веб-морд); остальные датчики как у desktop.
- Фон доверенной сети исключён всюду: 445/135/139 (SMB/RPC), 53/88/389/464/3268 (доменные службы).
- Порты 22/3389 не ловушки (заняты реальными сервисами), накрываются датчиками дверей.
- Состав профилей — конфигурируемый; дефолты только стартовая точка для полевого теста.

## Risks / Trade-offs

- [Обёртка wevtapi недокументирована в деталях] -> тонкий слой только под нужные 3 event ID; проверка фактического API на этапе реализации, интеграционный тест на реальной Windows-машине.
- [Разночтения сообщений sshd между дистрибутивами] -> парсер пишется по реальным образцам с целевых машин; нераспознанная строка не теряется, а пишется в лог агента для донастройки.
- [Маскировка ограничена уровнем баннеров] -> принято как граница ниши low-interaction honeypot; глубокий фингерпринтинг выявит ловушку — для сирены в доверенной LAN это приемлемо.
- [Telegram-лимиты при брутфорсе] -> агрегация до первого события + дайджесты; backoff на 429.
- [Self-signed сертификат на :443 выдаёт ловушку внимательному клиенту] -> стандарт для ловушек данного класса; при необходимости позже — реальный сертификат.
- [Событие Windows 4625 не всегда содержит IP источника] -> дублируем факт IP из 1149; отсутствие IP помечаем в алерте, а не молча пропускаем.

## Migration Plan

1. Сборка под обе платформы; ручной запуск с тестовым конфигом на одной машине каждой ОС.
2. Установка службы/юнита, проверка чтения журналов и ловушек «с себя» (telnet/nc на собственные порты).
3. Период приработки: заглушить в allowlist легитимных «стукачей» (антивирус, мониторинг), проявившихся в первые дни.
4. Откат: остановка и удаление службы/юнита; агент не меняет системных настроек (кроме собственного каталога и self-signed сертификата), поэтому откат тривиален.

## Open Questions

- Точный вариант обёртки EvtSubscribe — решается на этапе реализации (влияет только на внутренний слой, не на архитектуру).
- Формат итоговых Telegram-сообщений (детали вёрстки, язык) — уточняется на полевом тесте.
