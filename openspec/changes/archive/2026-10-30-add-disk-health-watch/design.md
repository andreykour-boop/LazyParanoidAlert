# Design

## Context

Агент — один бинарник `cmd/siren`: конвейер `runAgent` = ловушки (internal/trap) + двери событий (internal/doors) → `pumpEnrich` (allowlist по IP, обогащение) → агрегатор (окно, дедуп) → notifier (Telegram, retry/429). Конфиг — плоский JSON (`internal/config`), читается один раз на старте, `data_dir` для файлов состояния уже есть. Кросс-платформа: Windows (служба + GUI) и Linux (systemd), без cgo; сборка из Windows в linux. Развёрнуты обе платформы; у пользователя серверы с hardware и software RAID. Мотивация — proposal.md (Why), поведение — specs/disk-health-watch.

## Goals / Non-Goals

**Goals:**
- Планировщик по календарному времени (wall-clock) внутри существующего конвейера, без нового процесса.
- Единый снимок здоровья из двух слоёв (L2 массивы/тома, L1 физ. диски) с нормализованным статусом ok/warn/fail/unknown(причина).
- Диф снимков с сохранением состояния между рестартами; тревоги — сразу, отчёты — по расписанию.
- Доставка отчётов в Telegram без изменения существующего notifier-кода доставки (retry/429 переиспользуются).

**Non-Goals:**
- ZFS/Btrfs/LVM, сетевые шар, температурная телеметрия, износ SSD сверх счётчиков reallocated/pending.
- Поля секции `health` в Windows GUI (только config.json; в форму можно добавить позже).
- Реагирование агента (очистка дисков, перезапуск чего-либо) — только наблюдение и оповещение.

## Decisions

### 1. Новый пакет `internal/health` + runner в `runAgent`

Коллекторы, модель слоёв, диф и состояние живут в `internal/health`; планировщик — горутина `health.Runner` внутри `runAgent` рядом с существующими горутинами конвейера. Управление жизненным циклом — тот же ctx. Альтернатива (отдельный таймер-процесс/systemd timer) отклонена: второй юнит на машину против «один файл, скопировал и забыл», и состояние всё равно общее с агентом.

### 2. Двухслойная модель с нормализованным статусом

```
Snapshot
  L2: [{name, kind: md|pool|lvolume, state: clean|degraded|rebuilding|failed|unknown, reason}]
  L1: [{name, model, serial, state: ok|warn|fail|unknown, reason, realloc, pending}]
  volumes: [{mount, total_bytes, free_bytes}]
  errors: [{source, reason}]   // кто не смог быть собран и почему
```

Источники заполняют то, что видят: Linux — smartctl по /dev/sdX и /dev/nvmeXnY (перечень из /sys/block, без loop/ram/zram/removable) + `mdadm --detail` по массивам из /proc/mdstat; Windows — WMI (Get-PhysicalDisk / StoragePool) через go-ole. Vendor CLI (storcli/perccli/arcconf) детектится в PATH и, если есть, добавляет L1 за hardware-контроллером (smartctl -d megaraid,N). Уровень без источника честно попадает в `errors`/`unknown`. Альтернатива (отдельный сборщик на каждый тип RAID) отклонена — комбинаторика и дубли кода.

### 3. SMART MVP: статус + два счётчика

Статус утилиты (PASSED/FAILED, Healthy/Warning/Unhealthy) + reallocated/pending > 0 → warn. Альтернатива (полная таблица атрибутов, температура) отложена: требует парсинга vendor-специфичных строк и не нужна для «сообщить об изменении».

### 4. Диф и состояние: snapshot на диск, сравнение по ключевым полям

`data_dir/health_state.json` хранит последний снимок (атомарная запись tmp+rename, как в config.Save). Diff по: статус сущности, набор сущностей (появился/исчез), нарушения порога места. При старте — diff против сохранённого: изменения → тревоги, совпадение → тишина. Альтернатива (держать в памяти) отклонена: рестарт на время проверки молча съедал бы изменения.

### 5. Планировщик: привязка к календарю, не к интервалу

Горутина вычисляет ближайшее наступление (check_hour:00 daily; report_weekday check_hour:00 weekly) и спит до него через таймер, пересчитывая после каждого срабатывания. Проверка при старте — только diff против сохранённого снимка (см. решение 4), без «всё хорошо», чтобы рестарт службы не порождал рапортов. Альтернатива (time.Ticker 24h) отклонена: время плавает после рестартов.

### 6. Доставка: отчёты напрямую в notifier, тревоги — событиями

Еженедельный отчёт и повторные daily-предупреждения о месте идут напрямую в `notify.Notifier`/`Client` как готовое сообщение (мимо агрегатора: дедуп съел бы идентичный текст планового отчёта). Тревоги об изменениях — новые `Kind` (`disk_health_alert`, `disk_space_alert`) через общий конвейер event→notice, чтобы получить обогащение заголовка (agent name/IP) и единый формат. `kindLabel` в notify дополняется. Альтернатива (всё напрямую, без Kind) отклонена: тревоги теряют единый формат и пути тестирования конвейера.

### 7. WMI через go-ole (Windows), smartctl exec (Linux)

Windows-сборщик — COM/WMI через `github.com/go-ole/go-ole` + встроенный wmi-фолбэк через `exec powershell Get-PhysicalDisk` как запасной путь, если COM-запрос не удался (простота отладки). Linux — запуск `smartctl`/`mdadm` (exec), пути определяются в PATH; отсутствие — unknown(причина), не ошибка конвейера. Альтернатива (парсить /sys напрямую) отклонена: SMART в sysfs без утилиты неполон, а smartmontools пользователь согласился ставить (install.sh).

### 8. Секция `health` конфига: плоские поля, дефолты в applyDefaults

```json
"health": {
  "enabled": true,
  "check_hour": 9,
  "report_weekday": 1,
  "warn_pct": 10,
  "min_free_gb": 0
}
```
Валидация в config.validate (hour 0–23, weekday 0–6, pct 1–99, min_free_gb ≥ 0); отсутствие секции = дефолты (старые конфиги совместимы). `Save` сохраняет секцию как остальные поля. GUI не трогается.

## Risks / Trade-offs

- [smartctl требует root] → служба и так работает от SYSTEM/LocalSystem; на Linux юнит запускается от root (уже так для sshd-дверей).
- [vendor-зоопарк RAID-контроллеров] → MVP честно пишет «уровень контроллера» в отчёт; глубокая перечислительность (-d megaraid,N) включается только при найденном CLI, деградация функциональности не ломает конвейер.
- [Ложные тревогиPending-секторов на старых дисках] → pending/realloc > 0 = warn (не fail), в отчёте виден счётчик; порог можно будет ужесточить позже конфигом, не меняя спеку.
- [Часовой пояс/DST] → планировщик пересчитывает ближайшее время каждый цикл, сдвиг DST просто сдвигает следующую проверку; дубли исключены одноразовым срабатыванием на наступление часа.
- [Потеря Telegram в момент отчёта] → notifier уже ретраит и дренирует очередь; отчёт отправится после восстановления, доп. логика не нужна.
- [WMI через COM нестабилен на экзотических сборках Windows] → фолбэк exec powershell уже заложен; худший случай — unknown(причина) в отчёте, а не тишина.

## Migration Plan

1. Обновить бинарник на машинах (замена exe + рестарт службы, как в прежних изменениях); конфиг трогать не обязательно — секция `health` появится с дефолтами.
2. Linux: install.sh ставит smartmontools и nvme-cli перед установкой агента; на уже установленных — `apt install smartmontools nvme-cli` вручную или переустановка комплекта.
3. Первый отчёт приходит в ближайший report_weekday/check_hour; до этого работают только тревоги (включая diff при старте).
4. Откат: вернуть прежний exe; лишняя секция `health` старым бинарником игнорируется (JSON-парсинг без strict).
