# alert-delivery Specification

## Purpose

Доводка событий до владельца: обогащение IP до понятного идентификатора машины, агрегация повторов (брутфорс, сканирование) и доставка уведомлений в Telegram без превышения лимитов API и без потери событий.

## Requirements

### Requirement: Обогащение события данными источника

Система SHALL дополнять каждое событие hostname источника (reverse DNS) и MAC-адресом из ARP-таблицы, если они определены. Ручная карта «IP -> имя» из конфига SHALL иметь приоритет над reverse DNS. Результаты обогащения SHALL кэшироваться.

#### Scenario: IP разрешается в hostname

- **WHEN** формируется событие с IP источника, для которого существует PTR-запись
- **THEN** событие дополняется hostname из PTR-записи

#### Scenario: Ручная карта важнее DNS

- **WHEN** IP источника присутствует в ручной карте конфига и имеет PTR-запись
- **THEN** событие использует имя из ручной карты

#### Scenario: Неопределимый источник помечается

- **WHEN** reverse DNS и ARP не дают результата для IP источника
- **THEN** событие доставляется с IP и явной пометкой, что имя не определено

### Requirement: Агрегация повторных событий

Система SHALL агрегировать повторные события одного типа от одного источника за настраиваемое окно: получателю доставляется первое событие и периодический дайджест с количеством накопленных событий, а не каждое событие по отдельности.

#### Scenario: Брутфорс не порождает сотню сообщений

- **WHEN** один IP совершает 50 неудачных попыток входа за 5 минут
- **THEN** получатель получает событие о первой попытке и дайджест с итоговым количеством, но не 50 отдельных сообщений

### Requirement: Доставка уведомления в Telegram

Система SHALL доставлять каждое событие или дайджест в указанный конфигом Telegram-чат сообщением, содержащим: имя машины-агента с её локальным IP, время, тип события (попытка/вход/подключение к ловушке), порт и протокол, IP источника, hostname и MAC (если определены), учётную запись (для входов), а также пароль, предложенный клиентом ловушке, если он был захвачен.

#### Scenario: Событие доставляется полным сообщением

- **WHEN** формируется событие входа по RDP с известными IP, hostname и учётной записью
- **THEN** в Telegram-чат доставляется сообщение со всеми этими полями и именем машины с её IP

#### Scenario: Пароль от ловушки виден в алерте

- **WHEN** клиент вводит пароль SSH-ловушке и факт попытки формируется
- **THEN** сообщение в Telegram-чат содержит строку с предложенным паролем

### Requirement: Устойчивость доставки к лимитам API

При получении от Telegram API ответа об превышении лимита (HTTP 429) система SHALL повторять доставку с нарастающей задержкой и SHALL накапливать недоставленные события, не теряя их; события, не вошедшие в отложенную доставку, SHALL попасть в последующий дайджест.

#### Scenario: Событие переживает временный отказ API

- **WHEN** Telegram API отвечает HTTP 429 на попытку отправки
- **THEN** агент повторяет отправку с задержкой, а события, накопленные за время задержки, не теряются и доставляются позже

### Requirement: Разрешённые источники (allowlist)

Система SHALL подавлять доставку событий от источников из allowlist конфига: IP или CIDR-сеть с необязательным суффиксом портов. Запись без портов подавляет все события источника; запись с портами — только события перечисленных портов (ловушки на них и реальные входы по сервису порта: SSH — 22, RDP — 3389). События без привязки к порту и события других портов SHALL доставляться как прежде. Источник вне allowlist и источник с неизвестным IP MUST NOT подавляться.

#### Scenario: Запись без портов глушит источник целиком

- **WHEN** allowlist содержит «192.168.1.10» и этот хост подключается к любой ловушке
- **THEN** событие не доставляется в Telegram

#### Scenario: Запись с портом глушит только этот порт

- **WHEN** allowlist содержит «192.168.1.10:22», хост подключается к ловушке на порт 22 и затем к ловушке на порт 23
- **THEN** событие по порту 22 не доставляется, событие по порту 23 доставляется как тревога

#### Scenario: Реальный вход по разрешённому сервису подавляется

- **WHEN** allowlist содержит «192.168.1.10:22», хост успешно входит по SSH на машину с реальным sshd на порту 22
- **THEN** событие входа не доставляется, при этом его попытка входа с этого же хоста к другой ловушке остаётся видимой

#### Scenario: Событие без порта не подавляется записью с портами

- **WHEN** allowlist содержит запись с портами, а источник события не привязан к сервисному порту (порт события неизвестен)
- **THEN** событие доставляется как прежде

#### Scenario: Сеть с портами

- **WHEN** allowlist содержит «10.0.0.0/24:22,3389», хост из этой сети подключается к ловушке на порт 3389 и к ловушке на порт 5900
- **THEN** событие по порту 3389 не доставляется, событие по порту 5900 доставляется

### Requirement: Формат allowlist-записей

Конфигурация SHALL принимать allowlist-записи формата «IP[/CIDR]» с необязательным суффиксом «:порт[,порт…]» (порты 1–65535); для IPv6-адреса с портами — скобочная форма. Записи вне формата MUST отклоняться валидацией конфига с указанием номера записи.

#### Scenario: Некорректная запись отклоняется

- **WHEN** в конфиге allowlist содержит строку, не являющуюся IP, CIDR или записью «хост:порты» в допустимом формате
- **THEN** загрузка/сохранение конфига завершается ошибкой валидации с указанием номера записи

#### Scenario: IPv6-записи

- **WHEN** allowlist содержит «::1» и «[::1]:22»
- **THEN** обе записи принимаются: «::1» — адрес без портов (подавление всего источника), «[::1]:22» — запись с портом 22
