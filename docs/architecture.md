# Архитектура

Siren — одиночный бинарник-агент, который ставится службой на наблюдаемой
машине. Внутри — конвейер событий и sidecar-сторож здоровья. Поведение
зафиксировано спеками в [`openspec/specs/`](../openspec/specs/); этот документ —
обзорная карта.

```
 события-ловушки            факты входов              здоровье дисков
      |                          |                          |
 [ловушки: TCP-          [двери: Linux journald     [сторож здоровья:
  эмуляторы сервисов]     ssh unit / Windows          SMART, тома, RAID]
      |                   Event Log 4624/4625/1149]        |
      v                          v                         v
      +-----------+--------------+--------------------------+
                  |        pump: enrich
                  |   - выкидывает allowlist-источники
                  |   - ARP-таблица -> MAC
                  |   - имя: name_map -> reverse DNS
                  v
             [агрегатор]
   - окно aggregate_window_seconds на источник
   - всплеск сканирования -> один алерт «N событий»
   - брут-форс по портам -> сводный алерт
                  |
                  v
            [доставка Telegram]
   - алерты немедленно, дайджест по расписанию
   - retry с нарастающей задержкой при 429
```

## Ловушки (port-traps)

Ловушка — TCP-слушатель на порту с эмулятором известного сервиса. Любое
подключение (не только данные) — событие `trap_connect`: к порту кто-то
подключился, хотя нормального трафика на нём быть не должно. Эмуляторы:
`ftp`, `telnet`, `ssh`, `http` (+ TLS), `vnc`, `mysql`, `postgres`, `silent`
(порт отвечает молчанием). Набор портов задаёт профиль (`desktop` добавляет
80/443 — на рабочей станции входящий веб это аномалия) или явный список
`traps` в конфиге. Порт, занятый настоящим сервисом, пропускается с WARN —
за ним уже следит датчик входов.

## Двери (auth-event-monitoring)

Датчики реальных входов:

- **Linux** — чтение journald юнита `sshd_unit` (`ssh`/`sshd`): неудачные и
  успешные аутентификации по SSH.
- **Windows** — подписка на Event Log: Security 4624/4625 (входы,
  LogonType 10 = удалённый RDP) и RCM 1149 (исходящий RDP-клиент, источник
  пользовательских подключений).

Двери штампуют событие сервисным портом (SSH → 22, RDP → 3389), поэтому
allowlist-запись с портом гасит и ловушку, и реальные входы по этому сервису.
Дубликат «4624 + 1149 об одном факте» схлопывается.

## Allowlist

Запись формата `хост[/CIDR][:порт[,порт…]]` (IPv6 с портами — `[::1]:22`):

- без портов — гасит **все** события источника;
- с портами — только события перечисленных портов; событие без привязки
  к порту не гасится.

Невалидная запись в работающем конфиге (правка на лету) игнорируется
fail-open: источник остаётся видимым. Валидация при загрузке конфига —
fail-closed: плохая запись не даёт агенту стартовать.

## Агрегация и доставка

События одного источника внутри окна `aggregate_window_seconds`
схлопываются в один алерт со счётчиком. Счётчики с нулём не печатаются,
заполнителей «нет данных» нет. Доставка — Telegram Bot API; при 429 —
retry с нарастающей задержкой, потерянные события попадают в дайджест.

## Сторож здоровья (disk-health-watch)

Расписание: ежедневно в `check_hour` diff-проверка, в `report_weekday` —
еженедельный отчёт. Источники данных:

- **Windows**: WMI (`MSFT_PhysicalDisk`, `MSFT_StoragePool`), SMART-счётчики —
  smartctl (smartmontools, основной), фолбэк — root\wmi;
- **Linux**: `smartctl --scan`, nvme-cli, mdadm; vendor-утилиты RAID
  (storcli/perccli/arcconf) — опционально.

Отслеживаемые признаки: статус SMART/массива, деградация/перестройка RAID,
пропавший диск/том, свободное место ниже `warn_pct`/`min_free_gb`, **рост**
realloc/pending (SATA) и media errors (NVMe) — самый ранний признак
деградации, тревога даже при SMART «ok». База счётчиков хранится в
`data_dir/health_state.json`, переживает рестарт (изменения за простой
сообщаются).

`-health-report` — внеочередной человекочитаемый отчёт строго read-only:
ничего не пишет, ничего не отправляет.

## Управление (Windows)

Пульт в трее — тот же бинарник: установка/удаление службы, галочки ловушек,
настройки с валидацией и перезапуском службы, секция здоровья. Работающая
служба — единственный источник конвейера; пульт только управляет ею.
